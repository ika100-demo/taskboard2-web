# 001 — List tasks and create them with a form on the root page, calling taskboard2-api server-side

## Problem

Spec 001 gave taskboard2 an API to create and list tasks, but the tasks live only in the API's memory: every restart or redeploy wipes them (AC-001.12), and the API cannot run more than one instance without each one holding its own list. The only way to use the system is to send HTTP requests by hand, because the taskboard2 web app still shows only its template page. Now that tasks are worth keeping, they should go into a database, and people should be able to see and add tasks in a browser.

## System context

Slice of the system plan `002-persist-tasks-in-postgres-and-manage` in `ika100-demo/taskboard2-gitops` for `taskboard2-web` (web-nextjs). The system criteria and the contract below are binding: every criterion of this spec implements one of them and names it: `(system AC-<NNN>.<n>)`.

### System criteria

- **AC-002.7** Given tasks exist, including tasks created directly through the API, when a user opens the web app's root URL, then the page lists every task returned by `GET /tasks`, oldest first, each showing its title and, if it has one, its due date as `YYYY-MM-DD`; a task without a due date shows no date.
- **AC-002.8** Given no task exists, when a user opens the web app's root URL, then the page shows the text "No tasks yet." instead of a list.
- **AC-002.9** Given the web app's root URL is open, when the user enters a title (and optionally picks a due date) in the create form and submits it, then the new task appears at the end of the list without a manual page reload, the form is cleared, and `GET /tasks` on the API contains the task.
- **AC-002.10** Given the create form, when the user submits a title that is empty, only whitespace or longer than 200 characters, then the form shows an error message next to the title field, keeps what the user typed, and no task is added (the API's rules of AC-001.7 and AC-001.8 apply; the web app adds no rules of its own).
- **AC-002.11** Given the API is unreachable or answers `503`, when a user opens the root URL, then the page still loads and shows "Tasks could not be loaded. Please try again later." instead of the list; when the user submits the create form in that state, then the form shows "The task could not be saved. Please try again later." and keeps what the user typed.
- **AC-002.12** Given only the web app is exposed outside the environment and the API is reachable only inside it, when a user lists and creates tasks in the web app, then both work: the user's browser never has to reach the API directly.

### Contract

The API's HTTP contract is the one of spec 001 (system plan `docs/plan/001-create-and-list-tasks.md`, `## Contract`),
unchanged in fields, validation and `201`/`200`/`422` behaviour; this section restates what the web app needs and
adds the database-related parts.

### Base URL and configuration

- taskboard2-api: in-cluster `http://taskboard2-api` (Service port 80); dev public URL
  `http://taskboard2-api.taskboard2-dev.localhost:8088`. Reads `DATABASE_URL` (libpq URI, set by the platform from
  the `postgres` resource). Without `DATABASE_URL` it uses the in-memory store (tests and local runs only).
- taskboard2-web: reads `TASKBOARD2_API_URL` (no trailing slash; dev value `http://taskboard2-api`) on the server
  only. When it is unset, every API call counts as failed (AC-002.11 texts), and the app still starts and passes
  its probes.

### Task object

Exactly three fields: `id` (string, UUID4 canonical form, generated by the API, unique across restarts and
replicas), `title` (string, trimmed, 1 to 200 characters), `due_date` (`"YYYY-MM-DD"` or `null`, always present).

### `GET /tasks`

- `200` with a JSON array of task objects, oldest first (creation order), every task in the database; `[]` when
  empty.
- `503` when the database is unreachable or fails (body under Errors).

### `POST /tasks`

Request: JSON object, `Content-Type: application/json`, `title` (required string) and `due_date` (optional,
`"YYYY-MM-DD"` or `null`); the web app sends `due_date` as `null` when the date field is empty, and `title` exactly
as typed.

- `201` with the created task object.
- `422` on invalid input, validated before the database is touched (so an invalid body gives `422` even when the
  database is down).
- `503` when the database is unreachable or fails; no task is stored.

### Storage (taskboard2-api only)

```sql
CREATE TABLE IF NOT EXISTS tasks (
  seq      BIGINT GENERATED ALWAYS AS IDENTITY UNIQUE,  -- creation order
  id       UUID PRIMARY KEY,
  title    VARCHAR(200) NOT NULL,
  due_date DATE NULL
);
```

- `GET /tasks` is `SELECT id, title, due_date FROM tasks ORDER BY seq`.
- The schema is created by the API itself, idempotently, under `pg_advisory_lock` so two replicas starting at once
  do not race; it runs on the first successful database connection, not as a hard startup requirement.

### Web page (taskboard2-web)

- `GET /` renders: a list (`<ul>`/`<li>`, one item per task, title then due date) or "No tasks yet." or "Tasks could
  not be loaded. Please try again later."; and the create form (title field labelled "Title", date field labelled
  "Due date", submit button "Add task").
- Field errors from a `422` are shown next to their field; the generic save error of AC-002.11 is shown above the
  submit button.

### Errors

- `422` (API): the spec 001 format `{"detail": [{"loc": [...], "msg": str, "type": str}]}`; callers depend only on the
  status and the last element of each `loc` (`"title"` or `"due_date"`; `["body"]` or `["body", <pos>]` for a body
  that is not a JSON object).
- `503` (API, new): `Content-Type: application/json`, body `{"detail": "Task store unavailable"}`. Callers depend on
  the status only, not the text. Raised for any connection, pool-timeout or query error of the database.
- Any other status, a non-JSON body, a body that does not match the shapes above, a timeout or a connection error is
  a failed call. The web app treats a failed `GET /tasks` like `503` (load error text) and a failed `POST /tasks`
  like `503` (save error text, inputs kept); on a `422` whose `loc` names no known field, it shows the save error
  text. It never assumes a failed `POST` did not create the task; the next page load shows the truth.
- The web app logs failed API calls server-side (status, duration) and never forwards API bodies to the browser.

### Timeouts

- Web to API: 5 s per request (`AbortSignal.timeout(5000)`), for both `GET /tasks` and `POST /tasks`; no retry. A
  timed-out or refused call is a failed call (Errors). A retry by the user after a timed-out `POST` may create a
  duplicate, which AC-001.6 allows.
- API to database: connect timeout 2 s, pool checkout timeout 2 s, `statement_timeout` 3 s, so the API answers
  `503` well inside the web app's 5 s. The pool drops broken connections and reconnects on the next request
  (AC-002.5), with no restart and no background retry loop.
- When the API is down or restarting, the Gateway or the in-cluster Service refuses the connection or answers
  `502`/`503`: the web app shows its error texts and keeps serving its page and probes. When the database is down,
  the API stays ready and answers `503` with the JSON body.
- Smoke tests: 10 s per request (API, as in spec 001); Playwright's default timeouts (web).

### Provided by the system

The gitops part of this plan wires these for this repo; rely on them, do not ask for them again:

- exposed through the Gateway at host `taskboard2-web`
- env `TASKBOARD2_API_URL=http://taskboard2-api`

## Stories

- As a taskboard2 user, I want to see all tasks with their due dates when I open the web app, so that I know what is due without sending HTTP requests by hand.
- As a taskboard2 user, I want to add a task with a title and an optional due date in a form, so that I can record work in the browser and see it in the list right away.
- As a taskboard2 user, I want clear messages when my input is rejected or the task service is unavailable, so that I know whether to fix my input or try again later, and I never lose what I typed.
- As an operator, I want the browser to talk only to the web app, so that the task API does not have to be exposed outside the environment.

## Acceptance criteria

Smoke criteria (marked `(smoke)`) are checked after deploy using only the web app's public URL; the shared dev environment is never empty, so they find their own task by a unique title and never assume an empty list. Criteria serving system AC-002.8 and AC-002.11 need an empty or unreachable API and are checked in-process and in local end-to-end tests against a stub API only.

- **AC-001.1** Given the API's `GET /tasks` returns several tasks, including tasks created directly through the API since the page was last loaded, when a user opens the web app's root URL, then the page shows one list item per returned task, in the order the API returns them (oldest first), each showing its title followed by its `due_date` exactly as `YYYY-MM-DD`; a task whose `due_date` is `null` shows its title and no date. (system AC-002.7)
- **AC-001.2** Given a task was created through the form with a unique title and a due date, when the user reloads the web app's root URL, then the task is still listed, after the tasks that existed before it, with its due date as `YYYY-MM-DD`. (system AC-002.7) (smoke)
- **AC-001.3** Given the API's `GET /tasks` returns `[]`, when a user opens the web app's root URL, then the page shows the text "No tasks yet." and no task list. (system AC-002.8)
- **AC-001.4** Given the web app's root URL is open, then the page shows a create form with a text field labelled "Title", a date field labelled "Due date" and a submit button "Add task"; the title field carries no length, required or pattern restriction. (system AC-002.9) (smoke)
- **AC-001.5** Given the root URL is open, when the user enters a unique title, picks a due date and clicks "Add task", then without a page reload the new task appears as the last item of the list with its title and due date as `YYYY-MM-DD`, both form fields are empty again, and the API received exactly one `POST /tasks` with that title and due date (through the web URL alone this is observed by AC-001.2). (system AC-002.9) (smoke)
- **AC-001.6** Given the root URL is open, when the user enters a unique title, leaves "Due date" empty and clicks "Add task", then the API receives `due_date` as `null` and the new task appears as the last item of the list with no date. (system AC-002.9) (smoke)
- **AC-001.7** Given the create form, when the user submits an empty title, a title of only spaces, or a title of 201 characters, then the request reaches the API (the web app adds no rule and no trimming of its own), the text "Please enter a title of 1 to 200 characters." is shown next to the title field, the title and due date the user entered are still in the fields, and no task is added to the list (also not after a reload). (system AC-002.10) (smoke)
- **AC-001.8** Given the create form, when the user submits a title of exactly 200 characters, or a title with leading and trailing spaces, then the API receives the title exactly as typed and the list shows the task with the title the API returns (trimmed). (system AC-002.10) (smoke)
- **AC-001.9** Given the API answers `POST /tasks` with `422`, when the last element of a `detail[].loc` is `due_date`, then the text "Please enter a valid date as YYYY-MM-DD." is shown next to the "Due date" field; when no `loc` names `title` or `due_date`, then "The task could not be saved. Please try again later." is shown above the submit button; in both cases the inputs are kept, nothing is added to the list, and no text from the API's response body (such as its `msg`) appears in the page. (system AC-002.10)
- **AC-001.10** Given `GET /tasks` fails (the API is unreachable, refuses the connection, does not answer within 5 seconds, answers `503` or any status other than `200`, returns a body that is not a JSON array of task objects, or the API's address is not configured), when a user opens the root URL, then the page answers `200` and shows "Tasks could not be loaded. Please try again later." instead of the list, together with the create form. (system AC-002.11)
- **AC-001.11** Given `POST /tasks` fails (unreachable, no answer within 5 seconds, `503` or any status other than `201` and `422`, or a body that is not a task object), when the user submits the create form, then "The task could not be saved. Please try again later." is shown above the submit button, the title and due date the user entered are kept, nothing is appended to the list, and the call is not retried. (system AC-002.11)
- **AC-001.12** Given the API is unreachable or the API's address is not configured, when the web app starts and its liveness and readiness endpoints are called, then the app starts and both endpoints answer as healthy. (system AC-002.11)
- **AC-001.13** Given a user opens the root URL, lists tasks and creates a task through the form, when the browser's requests are recorded, then every request goes to the web app's own host and none goes to the API or any other host. (system AC-002.12) (smoke)

## Non-goals

- Editing, completing or deleting tasks.
- Pagination, search, filtering or sorting other than the API's order.
- Validation in the browser or in the web app (all rules are the API's, AC-001.7 and AC-001.8 of the API spec).
- Automatic retries of failed API calls, and preventing duplicates when a user retries after a failed or timed-out save.
- Showing the API's own error messages to the user.
- Date formats other than `YYYY-MM-DD` (no localisation).
- Sign-in or per-user task lists.
